## SPIA-style residual-context probe finding

See `tests/test_benchmark_suite.py::test_spia_residual_context_probe` and `tests/test_quasi_identifier_check.py` for the full case construction and assertions. Summary: a 10-row employee dataset is constructed so that one row (Alice Chen, VP of Engineering, Austin office) and one other row (a second VP, Remote office) are each the only row combining two individually-low-cardinality (and therefore `enum_kept`/kept-real-by-design) fields, `title` and `office` -- neither field alone is unique in the dataset (two rows share the VP title; five rows share the Austin office), only the *combination* is. Their literal names/emails ARE masked correctly (Privacy Score 1.0 for this case, independent of the finding below).

**Originally, when this finding was first produced (initial Phase 10 run), this project's masking did NOT catch this.** Phase 2's shape-based column rules classified each column independently, with no cross-column uniqueness analysis anywhere in the pipeline.

**This has since been addressed with a v1 mitigation, added before Phase 11, not deferred.** `record_masker.py` now checks the joint tuple of every currently kept-real (`enum_kept`/`boolean_kept`) column across a batch; a row whose combination is unique (or near-unique, configurable via `quasi_identifier_max_group_size`, default strict uniqueness) has those specific columns redacted *for that row only* -- other rows sharing the same column are untouched. Verified directly: both flagged rows in this case now have `title`/`office`/`department` redacted; the other 8 rows keep their real values. See `record_masker.py`'s `_find_quasi_identifier_risk` for the exact design and its documented reasoning for why checking the single full joint combination (rather than every subset) is sound, not an incomplete shortcut.

**The mitigation's scope is deliberately narrow, and is NOT a general fix for re-identification risk -- stated plainly rather than overclaimed:**
- It only considers columns already classified `enum_kept`/`boolean_kept`; it has no opinion on `default_masked`/numeric/date columns (already masked/transformed regardless).
- It checks ONE joint combination (all currently-kept-real columns together in a batch), not arbitrary configurable subsets, and is not general k-anonymity/l-diversity tooling.
- A `never_mask` override on a contributing column removes that column from consideration entirely (by design, consistent with override precedence) -- a user-forced-real column can still combine with others to create a residual risk this check will not catch.
- It only reasons about uniqueness *within the batch actually sent* to the LLM in one request -- it has no model of a larger population or external knowledge a reader might bring to bear, and it does not persist state across separate requests/batches.
- This is a real, disclosed limitation of the mitigation itself, not something tuned away -- cited specifically in Phase 11's "what this protects against, and what it doesn't" documentation.

## What was and was not measured

- **Privacy Score** (all three conditions, all 36 cases): measured for real in this run, mechanically (verbatim substring absence), no LLM involved.
- **Manual-override hard pass/fail tests**: measured for real, deterministic, no LLM involved. See `test_override_hard_pass_fail_*` in `tests/test_benchmark_suite.py`.
- **SPIA-style residual-context probe**: measured for real against actual masking output (not a numeric score, a documented finding). The v1 mitigation this finding prompted is also verified for real, directly against masking output, not just asserted -- see `tests/test_quasi_identifier_check.py` (8 dedicated tests: correct redaction, no false positives on genuinely non-unique data, the `never_mask` escape hatch, the enable/disable toggle, near-unique group thresholds, boolean-column participation, and audit-log entry correctness with no real values logged).
- **Utility Score / Balanced Score**: NOT measured in this run. A real Anthropic client was actually configured and attempted (`claude-haiku-4-5`, current model ID as of this phase -- the project's previous hardcoded default, `claude-3-5-haiku-20241022`, was found stale/retired during this work and updated) -- the call failed with `Your credit balance is too low to access the Anthropic API`, an account billing condition, not a harness or code defect. The harness's judge-invocation and response-parsing logic IS tested for real against a fake/deterministic `judge_call` (see `test_utility_score_*` in `tests/test_benchmark_suite.py`) -- that proves the harness's plumbing works; it is still not a real utility measurement. Re-run once the account has sufficient credits to get actual numbers.
- **PII-Bench's published numbers**: copied verbatim from the project spec (arXiv 2502.18545), NOT independently reproduced -- different benchmark cases, different detectors, different (or no) judge model. Any resemblance to this project's numbers is suggestive, not a controlled comparison.
